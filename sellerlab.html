PROJECT OVERVIEW / 项目概览

从“看到波动”，走到“知道下一步查什么”。

Seller Lab 面向店铺经营人员。经营看板能够告诉用户销售发生了变化，却常常留下三个问题：变化来自哪里、哪些解释已有证据、下一步应该调查什么。

需求切入来自医药企业业务交流中的电商分析需求；实现与验证采用公开 Olist 历史交易数据及合成演示订单，不使用该客户的经营数据。当前为可运行研究 Demo，未完成真实商家生产部署。

用户任务

经营人员先识别关键问题，再核对证据、决定调查顺序；不要求先学会写 SQL。

我的角色

牵头业务问题定义、指标与异常框架、诊断交互和评测设计；独立开展原型、代码迭代与结果复盘。

BUSINESS QUESTION / 业务洞察

订单约增 7%，为什么商品金额反而约降 8%？

在同一卖家、相邻完整历史月份、已交付订单口径下，订单从 73 单增至 78 单，但商品金额从 R$ 7,546.70 降至 R$ 6,972.30。每单商品金额下降约 13.5%，抵消了订单量增长。

商品金额 = 去重订单数 × 每单商品金额
指标2018.062018.07变化
去重订单数7378+6.8%
已交付商品金额（BRL）7,546.706,972.30−7.6%
每单商品金额（BRL）103.3889.39−13.5%
+ R$ 516.90订单量变化的算术贡献
− R$ 1,091.30每单金额变化的算术贡献

分解约定：订单贡献 = 订单差 × 上期每单金额；每单金额贡献 = 本期订单数 × 每单金额差，两项相加等于金额变化。数据源为 Olist，按 seller_id 筛选；不代表中国医药电商或单一渠道。商品金额只含商品明细价格，不含运费、退款、成本及平台费，不称为 GMV、净收入或利润。

PRODUCT DECISIONS / 关键产品设计

先确定诊断路径，再讨论智能程度。

先核对订单与每单金额，再下钻品类与 SKU

检查时间窗口、订单状态、金额定义与缺数情况；确认商品金额下降是否来自订单价值变化。接着比较品类金额差额和 SKU 贡献，只描述算术来源，价格、折扣和流量原因仍需补数。

异常不是一种问题

以量额、结构、贡献和趋势四类关系组织诊断路径。用户不需要先选择技术工具，而是从经营疑问进入对应分析。

把事实、假设和数据缺口分开展示

SQL 可以证实“某品类金额下降”，不能直接证实“竞争对手抢走客户”。报告让用户看到已核验发现和下一步补充材料。

按影响、证据充分性与可控性排序

优先呈现金额影响较大、数据支撑充分、经营者能够调查的问题。排序是业务判断规则，不把 LLM 的语气强弱当成可信程度。

把下一步建议变成可交接的调查任务

用户确认后再加入行动中心；任务保留商家、月份、证据与反馈。公开 Demo 的任务仅保存在浏览器会话，不自动改价或投放。

AI WORKFLOW / 系统与边界

让 SQL 算清楚，让 Agent 探索分析路径。

识别异常 / 确认任务

先核对商家、月份、统计粒度与支持范围。明确问题直接执行确定性契约，模糊问题先澄清或由用户确认有限方案。

指标拆解 / 数据下钻

只读 SQL 工具计算月度指标、品类 / SKU 贡献与履约指标；返回查询参数、结果、证据 ID 和范围。

假设验证 / 完成度核验

研究版模型可动态选择工具；程序核验引用与任务目标。缺数据、越权、预算耗尽或服务异常时停止，保留未完成状态。

问题排序 / 行动建议

输出已核验事实、待验证原因与核查事项，由经营人员决定下一步。历史回放的下月变化不能解释为行动带来的效果。

分工适合承担的任务约束
SQL / 确定性规则指标计算、范围过滤、证据渲染、任务完成度检查固定商家范围、参数化只读查询；数字不由模型自由生成
研究版 Agent多步规划、工具选择、复杂问题探索模型适配与挑战集已有记录；服务中断仍是实际问题
公开在线 Demo规则巡检、确定性 SQL、报告与证据复核不调用付费模型；不是已部署的自主经营 Agent
人工核查外部原因、决定经营动作与投入最终决策由人负责，系统不自动执行经营操作

EVALUATION / 对照与迭代

Agent 是否更好，要放在相同任务下比较。

48 项离线挑战任务覆盖指标、贡献拆解、复合问题、缺数停止与权限边界。标准答案由独立 SQL 从原始 CSV 重建，避免让待测系统自己生成答案。评测分开观察任务成功、事实正确、证据关联、正确停止、工具调用与耗时。

实验记录结果产品含义
首次真实模型挑战集Agent 41/48；强化 SQL 48/487 项因模型服务中断未完成；成功输出的结构化事实 37/37 正确
混合故障注入开发评测混合完整成功 27/48；纯 Agent 9/48超时回退能提供部分价值，但仍有 12 次错标完成
任务契约与确定性修复同题迭代后 48/48，错标完成 0零模型模式同样通过；证明有限规则覆盖，未证明模型增益

Bad Case：服务中断让任务没有结果

保留原 41/48 首次成绩，增加受限重试与明确降级；不能删去失败任务后重算成功率。

Bad Case：给了摘要，却没回答完整问题

将任务目标显式化，检查范围、排名和下钻依赖。未完成的目标不能因为语言流畅而被标成“成功”。

迭代决策：标准问题直接走确定性执行

模型价值集中在开放问题与分析路径探索；有限规则可以解决的问题不必为 Agent 增加延迟和不稳定性。

数据依据：仓库 README、evaluation-v0.8、首次真实模型与后续迭代记录；基线、脚本规划器、真实模型、同题复测分别记录。简历中的早期 65%→86%、建议有效率 91% 和耗时降低 97% 缺少可公开对齐的原始评测口径，暂不作为本页复现实验结论，待补充样本与计时定义。

RESULTS & NEXT / 结果与下一步

目前验证了可核对的诊断方法，下一步验证真实决策价值。

项目完成了从真实历史交易数据、异常框架到可运行工作台、独立 SQL 对账与多轮评测的研究过程。它体现了我在指标拆解、Agent 分工、交互与失败分析上的产品实践；尚未证明真实商家的销售或利润提升。

下一步会用真实经营任务观察：用户是否更快定位重要问题、能否理解证据与判断边界、调查建议是否被采用，以及额外分析成本是否值得。对照实验将同时记录任务质量、人工净耗时、模型调用成本与用户决策，保持相同观察窗口。
